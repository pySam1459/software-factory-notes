# MCP or CLI? Yes. (@zeeg)

Source: [@zeeg's X Article, 10 Nov 2026, 18:38 Europe/London](https://x.com/zeeg/status/2120224571689484639), with the same text on the [Sentry blog](https://blog.sentry.io/mcp-or-cli/). David Cramer, Sentry's founder, argues that agents with a sandbox should use both, not pick a winner. The article body was read from the X `article` field and checked against the blog mirror; WebFetch of the X URLs returned 403.

## What the article argues

Sentry is shipping a unified flow: install the [new `sentry` CLI](https://cli.sentry.dev/commands/mcp/) (not the older `sentry-cli` CI tool), run `sentry auth login` (usually a device-code flow), then start the MCP server with `sentry mcp`. That command launches the existing MCP server over stdio and adds a shim so the CLI's stored login is reused. No separate MCP login is required.

The technical hook is a second token header. The hosted MCP service is a distinct OAuth proxy (CIMD/DCR on top of Sentry's provider). A normal `Bearer` token is treated as that MCP OAuth grant. A `Sentry-Bearer` token is treated as a raw Sentry API token and skips that proxy. Cramer presents this as a way to avoid historical MCP auth bugs by controlling the login himself. He also says it is not the long-term answer: consolidated MCP authentication is better for organisation-wide policy and native client token handling.

CLI and MCP share a lot of code, but they are not substitutes. The CLI has a filesystem, so an agent can pull a large raw log (the article's example is session replay events), then grep, paginate and reason over it in chunks. He argues a sane MCP tool result cannot return that volume, and reimplementing those behaviours on the server is not worth it. MCP, meanwhile, is the better agent interface: tools are discovered natively, without first teaching the model that a CLI exists. Combining them, a tool such as `get_session_replay` could tell the agent to finish the fetch with the CLI. **That transport-specific steering is not shipped.** The article says they know when the server was launched from the CLI, and that changing tool responses by launch path is "top of mind", not done.

A third section is about uneven MCP adoption: deferred tool loading and tool search differ by harness, the `instructions` metadata is not uniformly supported, and MCP Events is "largely not usable today". The close is practical: this is an experiment around today's limits, and Sentry is shifting onboarding toward a CLI-based approach rather than a plugin-based one.

## What checks out, and caveats

[Official CLI docs](https://cli.sentry.dev/commands/mcp/) confirm `sentry mcp` starts a local stdio server from the active CLI session and can be limited to an organisation or project. The [sentry-mcp security notes](https://github.com/getsentry/sentry-mcp/blob/main/docs/operations/security.md) confirm `Authorization: Sentry-Bearer <token>` bypasses MCP OAuth, passes the token through without storing, exchanging, refreshing or pre-validating it, and defaults those sessions to all active skills (narrowable with skill query parameters). Token lifetime and revocation stay with the caller and Sentry's API.

Cramer's own caveats matter. Steering by launch path is planned, not implemented, so do not treat "the same tool already returns different instructions on stdio versus HTTP" as a current behaviour. He also does not claim MCP will vanish: [in a reply to @hughhan](https://x.com/zeeg/status/2120254766299414787) he says the two are not fully interchangeable, and that if MCP solved the problem they would not bother with a CLI, but he does not think MCP will ever be the only thing they need.

Security questions in the thread were unanswered: whether the CLI token is org-wide versus OAuth-narrowed (@jus_eng_njainam, @UeI3erBJq2aqBwK), token lifetime, and whether org auth policies still apply (@kolovskydev). The security notes explain the bypass and the broader default skill set. They do not settle those policy questions.

## GHCP mapping

This is a proposed port, not a Sentry or GitHub product claim.

For the Copilot coding agent, put MCP servers in the repository [MCP settings JSON](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers). GitHub documents that cloud agent and code review support **tools only**, not MCP resources or prompts, and do not currently support remote servers that use OAuth. Allowlist specific tools rather than `*`; the agent will call them without asking. Secrets and variables must be prefixed `COPILOT_MCP_` and referenced as `$COPILOT_MCP_…`. GitHub's own Sentry example uses a local `@sentry/mcp-server` process and `SENTRY_ACCESS_TOKEN`. That fits unattended runs better than a device-code login, which a cloud-agent session cannot complete in a browser. Install the `sentry` CLI (and `gh`, if needed) in [`.github/workflows/copilot-setup-steps.yml`](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment). Prefer a least-privilege token scoped to one org or project, not a personal login with every skill enabled.

Use MCP for discovery and small, structured lookups. For large traces, replays, attachments or App Insights exports, follow Cramer's pattern: fetch to disk in the Actions runner workspace, then analyse with local tools. Do not try to return those payloads as MCP tool results. Write a short manifest beside the files (source IDs, time range, filters, fetch command and checksum) so a finding can be traced to its input, as @jul1anodev suggested. Put the same "when to use the CLI versus MCP" rule in a [Copilot skill](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills).

Keep the [coding-agent firewall allowlist](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall) tight (only the Sentry hosts you actually need). For local interactive work, configure MCP separately in [Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers) (`~/.copilot/mcp-config.json` or project `.mcp.json`) and in [VS Code agent mode](https://docs.github.com/en/copilot/how-tos/copilot-in-your-ide/customize-copilot/extend-copilot-with-tools-and-context/extend-copilot-chat-with-mcp) (`.vscode/mcp.json`). Those clients can use `sentry mcp` after a human has run `sentry auth login`; the cloud agent still needs a scoped secret.

Related: [agent-browser versus Playwright MCP](2026-11-08-blob16exe-agent-browser.md), which makes the same point that a CLI with a filesystem and an MCP tool interface solve different jobs, and that GitHub already ships a default Playwright MCP.
