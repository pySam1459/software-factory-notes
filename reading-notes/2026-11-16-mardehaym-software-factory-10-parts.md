He is founder of [@LimestoneHQ](https://x.com/LimestoneHQ), which embeds AI engineers into portfolio companies. Treat "our design" (two CI runs, then stop with a report in the ticket) as his own setup, self-described, not an independently checked system. The post is a clear checklist, and it is also a sales thread.

## The claim

A software factory takes a ticket in and returns a reviewed pull request. The work splits three ways: code handles every step it can check, agents handle the few steps that need judgement, and people own the spec, the hard decisions and the merge. The rule: "if code can check it, code does it." An agent saying the tests pass does not count. CI decides.

What does not qualify, in his telling: giving every engineer an AI coding tool; one agent with access to the repo (that is the loop, without the factory around it); a swarm that shares one long conversation and spends tokens rereading everything; a line that only works while your code and staging data sit on a vendor's servers.

Architecture, new domains, greenfield, big refactors, performance work and product discovery stay with people. The factory is for work that is well specified and checkable.

The slowest part, he says, is intake. Most backlogs do not have acceptance criteria that code can check, rewriting tickets takes time, and nobody volunteers.

The vendor test, "including ours": if you stop paying the vendor tomorrow, does the factory keep running? If it does not, you are renting the production line. The TL;DR is that most of the factory is the platform under the agent (gateway, measurement, gates and evals). Build those first on the stack you already own. Adding the agent is the easiest part.

## The ten parts

1. **Intake.** A status in the tracker starts the run. If the ticket has no acceptance criteria that code can check, it goes back instead of getting built.
2. **Spec and plan.** Before any code, the run lays out what it will build and how. A person approves that plan in the ticket, while a misunderstanding still takes minutes to fix.
3. **Orchestrator.** Every ticket follows the same fixed steps, inside a budget for CI runs, attempts, time and money. In his design, a run gets two CI runs. If the second is still red, it stops and leaves a report in the ticket.
4. **Sandbox.** Every task gets a fresh sandbox, with no credentials inside and an allowlist for outbound connections. When the task ends, the sandbox is thrown away.
5. **Gateway.** Every model call in the company goes through one gateway you host. Each team and service gets its own key and spend cap. Switching models is a config change.
6. **Context.** The agent uses a map of the code to see what depends on what, then pulls only what it needs.
7. **Gates.** CI decides whether the work passes. Deleting a test sends it back. The agent cannot change its own rules, a review agent has to quote the code it flags, and a person merges every pull request.
8. **Evals.** Prompts live in git. A prompt change only ships after it passes test cases built from real past pull requests.
9. **Measurement.** Every change connects the session, commit, pull request, ticket and epic, so you can see what a feature cost and how long it took. Report this by team, never as a ranking of individual developers.
10. **Seats.** Engineers' own AI tools connect directly to their vendors. Track that usage through metadata only: who uses what and what it costs. No prompts or code.

## GHCP mapping

This is a proposed port onto Sam's factory (GitHub, Copilot coding agent on Actions, pstack), not a claim that GitHub ships these ten parts as one product. Several of them have a documented hook. A few do not, and those gaps matter because of his own vendor test.

**1. Intake.** [Issue forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms) and [issue templates](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository) can require an acceptance-criteria field. A required textarea is not the same as criteria that code can check, so add a [GitHub Agentic Workflow](https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows) (or a plain Actions job) that bounces issues lacking testable criteria, in the spirit of the cancellation example above. An agent can draft those criteria, as @fahdmaatoug9 suggested, but a person should approve them before the run starts. Once the ticket is ready, you can [assign the issue to Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task). Docs are explicit that assigning an issue always creates a pull request, so this path is not a plan-first gate on its own.

**2. Spec and plan.** Docs do support a plan step, but not exactly "approve the plan in the ticket, then the run may start." In the IDE, [plan mode](https://docs.github.com/en/copilot/how-tos/copilot-in-your-ide/use-copilot-agents/use-plan-mode) researches the task and does not change code until you approve. The Copilot app has a Plan session mode with the same idea: [agent sessions](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions). For the cloud agent, docs describe a conversational loop: ask it to [create a plan, refine it, then say to implement the plan](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/research-plan-iterate). You can also write a [custom agent](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/create-custom-agents) that only posts a plan comment and stops, and require a human label or comment before a second job starts the coding agent. That last arrangement is something you build. It is not a first-class ticket-approval product on the assign-an-issue path.

**3. Orchestrator budget.** There is no documented "two CI runs then stop with a report in the ticket" knob. You can get close with three separate controls: job and step [`timeout-minutes`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) on Actions; [premium request allowances and budgets](https://docs.github.com/en/copilot/how-tos/manage-and-track-spending/manage-request-allowances) at organisation or enterprise level (these cap spend, not CI attempts on one ticket); and a stuck Actions coding-agent session that [times out after an hour](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/troubleshoot-cloud-agent). The Copilot SDK has [session limits](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/session-limits) (`maxAiCredits`), which is not the same as the cloud coding agent. The two-run stop, the ticket report, and "a flake rerun is not an attempt" are workflow and policy you write yourself. Keep CI honest, as the [@pontusab](2026-11-15-pontusab-ci-under-2-minutes.md) prompt also insists: no hidden retries.

**4. Sandbox.** This is the closest match. The coding agent runs in an ephemeral [Actions or cloud sandbox](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/manage-copilot-in-the-cloud), thrown away at the end. A [firewall with a recommended allowlist](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall) is on by default, and organisations can tighten or disable it. Docs also list limits: the firewall applies to processes the agent starts in the Actions appliance, not to MCP servers or setup steps, and it is not a complete security boundary. The agent does not receive ordinary repository or organisation Actions secrets; only [secrets and variables configured for the agent](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/configure-secrets-and-variables) are passed in. Keep that list short, which is the "no credentials inside" rule as far as GHCP will go. @ranuk_dev's warning still applies if you later widen that list or let the agent rewrite config.

**5. Gateway.** Be honest: GitHub Copilot does not give you a self-hosted model gateway that every company call goes through, with per-team keys you hold. What docs do support is [configuring which models users can access](https://docs.github.com/en/copilot/how-tos/copilot-on-github/set-up-copilot/configure-access-to-ai-models), plus [bring your own key](https://docs.github.com/en/copilot/concepts/models/bring-your-own-key) in two forms. Organisation or enterprise custom models (public preview) keep provider keys in GitHub settings and still route requests through GitHub's Copilot API, with usage in Copilot metrics. User-configured BYOK in a client talks to the provider directly and is a weaker fit for a company gateway. Spend caps are the premium-request budgets above, not per-team keys on a box you run. Switching models can be a policy change. It is not "a config change on a gateway you host."

**6. Context.** Closest documented pieces: [repository custom instructions](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions) (`.github/copilot-instructions.md` and path-specific instruction files), [`AGENTS.md`](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions), [Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory) (useful for learned facts, not a substitute for rules that must always apply), and [repository indexing for Copilot](https://docs.github.com/en/copilot/concepts/prompting-and-context/repository-indexing), which builds a semantic code-search index for Chat and the cloud agent. That is search and instructions, not a first-class "map of what depends on what" that shrinks a legacy repo to a handful of files on its own. You can add a generated code map to the repo or to instructions, but GHCP does not ship that map as a product.

**7. Gates.** This is the strongest documented set, and it is the part to copy first. [Branch rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) can require status checks and reviews. [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) plus "Require review from Code Owners" can protect `tests/`, `.github/workflows`, `.github/agents`, `AGENTS.md`, instruction files and the CODEOWNERS file itself, which is the practical form of "the agent cannot change its own rules." Docs for the cloud agent are explicit: a human must [review and merge](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations); the agent cannot mark its PR ready, cannot approve or merge, and the person who asked for the PR [cannot be the approving review](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output). By default, [Actions workflows on the agent's PRs do not run](https://docs.github.com/en/copilot/tutorials/cloud-agent/build-guardrails) until someone with write access approves them (this can be turned off, so treat it as a setting to keep). CODEOWNERS on `tests/` requires a review; it does not, by itself, fail a deleted test. Add a required check that fails when tests are removed without an agreed label or review, and remember @petrusenko_max and @san3xr: a missing test or a weak assertion still goes green. A review agent that must quote file, line, failure, smallest fix and blocking status is a custom agent or review prompt, as @teaser380 described, not a GitHub-enforced quote rule. See also [three review levers (@BHolmesDev)](2026-11-13-BHolmesDev-three-review-levers.md) and [agents complain (@kentcdodds)](2026-11-15-kentcdodds-agents-complain.md).

**8. Evals.** Prompts, custom agents and skills can and should live in git, which is the portable half of this part. Test cases built from past pull requests are a practice you design, already argued in [evals skills](2026-10-30-evals-skills.md) and [evals as an underrated skill](2026-10-29-evals-underrated-skill.md). Do not lean on `gh models eval`: [GitHub Models was retired on 30 July 2026](https://docs.github.com/en/github-models), including the playground, catalogue, inference API and that product's BYOK. A prompt-eval job in Actions, against fixtures mined from past PRs, is the path that still matches "if code can check it, code does it."

**9. Measurement.** [Copilot usage metrics](https://docs.github.com/en/rest/copilot/copilot-usage-metrics) and [team-level metrics](https://docs.github.com/en/copilot/reference/copilot-usage-metrics/team-level-metrics) exist, which supports reporting by team rather than a league table of individuals. Agent commits include a [link to the session logs](https://docs.github.com/en/copilot/responsible-use/agents), and an assigned issue is linked to the PR, so session, commit, PR and ticket can be tied together. An epic, and a single "what this feature cost" figure, are something you stitch from those links plus Actions and model spend. The metrics API is usage telemetry, not a full cost ledger, and session logs are more than metadata.

**10. Seats.** [Seat management](https://docs.github.com/en/rest/copilot/copilot-user-management) and usage reports cover who has Copilot and, in aggregate, how it is used. That is close to "who uses what and what it costs." It is not a complete metadata-only picture of every engineer's AI tool, because people will also use other vendors (his own part 10 assumes that). If you want "no prompts or code" in the seat report, do not treat raw session logs as the seat report.

**Always-on and pstack.** A factory that starts from a ticket status is closer to [always-on agents (@TekonBurns)](2026-11-13-TekonBurns-always-on-agents.md) than to a chat window, but the ticket still needs the intake gate. [pstack](2026-10-28-pstack-plugin-vs-copied-skills.md) can hold portable skills and instructions in git; it does not replace CI, rulesets or the merge. Related factory write-ups already in the repo: [two loops (@bholmes)](2026-10-30-bholmes-factory-two-loops.md), [software factory lessons (@andrestaltz)](2026-11-10-andrestaltz-software-factory-lessons.md), [factory diagram (@EnoReyes)](2026-11-06-EnoReyes-software-factory-diagram.md), [don't vibe-code your factory (@zachlloydtweets)](2026-11-04-zachlloydtweets-dont-vibe-code-your-factory.md), and [agent identity (@berman66)](2026-11-11-berman66-agent-identity.md).

## The vendor test, against an all-in GHCP stack

His test is the right question, and it is awkward for a factory that is all-in on GitHub Copilot. GHCP is a vendor stack. If you stop paying GitHub and Copilot tomorrow, the coding agent, the cloud sandbox, Memory, model access, premium-request budgets and the metrics API stop with them. You are, in his words, renting that part of the production line.

What can keep running is the platform he says to build first, if you have kept it in git and in Actions: issue forms and checkable criteria, plan comments and approval labels, CI gates, CODEOWNERS and rulesets, required checks (including a deleted-test check), prompt files, custom agents, skills, eval fixtures, and the habit of reporting by team. Those pieces are portable to another agent, or to no agent, which is the point of "if code can check it, code does it." The self-hosted gateway, and a metadata-only view of every seat outside Copilot, are the parts GHCP does not give you, and would have to be built or accepted as a gap.

The useful move is not to pretend GHCP is vendor-independent. It is to put the gates, evals, prompts and intake in the repo so the line still has a shape if the agent has to be swapped.
