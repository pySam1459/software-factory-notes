# One account per agent, and what that does not fix (@berman66)

Source: [@berman66, 11 Nov 2026, 20:00 Europe/London](https://x.com/berman66/status/2120607519059951985). He is CEO of [@runlayer](https://x.com/runlayer). The full text was in the post's `note_tweet`; the timeline card is truncated. This is a vendor pitch. The "public company" that went from zero MCP servers to "130+" in a year is an anonymous, self-reported customer anecdote, not a named or independently checked claim. The "CIO" quote "None of which is ideal" is likewise unsourced.

## What the post argues

@berman66 says the CIO's "biggest new problem" is that agents either borrow the user's permissions or run on a service account, "none of which is ideal," and "or the right way to do it." If the agent has the user's permissions, "it's usually too much for what the task actually needs" and "any prompt injection has the user's full blast radius." If it has a service account, "it's typically shared between several agents, and you can't tell which agent did what."

The product claim is that every Runlayer agent gets its own "agent account": "a Runlayer-native identity with its own Client ID/secret, policies, delegations, tokens and audit trail." He would not "run production workloads any other way." Treat that last sentence as an opinion and a sales close, not evidence that this is the only workable pattern.

The useful distinction in the post, even after you discount the pitch, is between three identity choices: impersonate the user, share a powerful service account, or give each agent a distinct identity with its own audit trail. The first two failure modes are real even if the 130-MCP figure is not.

## What the replies add

Nine replies, all direct to the original post. @berman66 had not replied in the thread when it was read.

[@johnroodepic](https://x.com/johnroodepic/status/2120610335807938565) has the sharpest objection: a per-agent account "fixes the log, not the blast radius." A list of 130 MCP servers is "a scope list nobody reads." What actually holds is "a token that expires with the task instead of an identity that lives as long as the agent."

[@mdp_sec](https://x.com/mdp_sec/status/2120616948463767623) makes the same point more briefly: a separate account helps you see who did what, "but an injection still rides whatever that account can reach."

[@mohammadvazin](https://x.com/mohammadvazin/status/2120614857774956556) says the service-account route "usually ends with one agent holding the union of everyone's access," and would rather see "short-lived tokens minted per task on the user's behalf, scoped to the one tool it needs."

[@jatingargiitk](https://x.com/jatingargiitk/status/2120614625373020414) asks what happens to permissions already delegated to an agent when the employee loses access. [@Alanogrok](https://x.com/Alanogrok/status/2120619494423032116) answers in the same direction: a separate identity helps attribution, but delegated permissions need "a clear expiry and revocation path, not just a clean audit log," especially when the original user's access changes.

[@jurlycat](https://x.com/jurlycat/status/2120615835324854605) asks, at 130 MCP servers, how you revoke stale agent access. [@rachbelaid](https://x.com/rachbelaid/status/2120609325807014141) reports a related operational problem: new or changed MCP tool descriptions can affect agent behaviour, and asks whether tool-description injection will become an attack. [@amirsadjady](https://x.com/amirsadjady/status/2120609545479471612) calls shared service accounts "the office fridge of permissions."

[@zayyenpatel](https://x.com/zayyenpatel/status/2120627491689881859) replied with a plug for Coworker. Note it as a product plug only.

Taken together, the thread accepts that a named identity per agent is better than a shared service account for attribution, and then insists that attribution is not a substitute for least privilege, a short lifetime, and revocation when the human owner loses access.

## GHCP mapping

This is a proposed mapping onto GitHub Copilot, not a claim that GitHub ships Runlayer-style agent accounts, and not a validation of the 130-MCP anecdote.

**Identity and review.** Copilot coding agent (docs now often say "Copilot cloud agent") acts as Copilot, not as the assigning user. [Commits are authored by Copilot](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations), with the person who assigned the issue or requested the change marked as co-author. Those commits are signed ("Verified"), and each commit message links to the [session logs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents). Copilot cannot mark its draft pull requests as ready for review, and cannot approve or merge them. If the repository requires approvals, [the person who asked Copilot to open the pull request cannot provide a counting approval](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output): another reviewer must approve. When Copilot opens a pull request under its own app identity, [an extra approval is required](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) if the repository already requires at least one. That extra rule is on by default in rulesets (an administrator can turn it off) and always applies to classic branch protection. Shared automations are attributed to Copilot and get that extra review; personal automations are attributed to the user who created them, and that user still cannot approve the pull request.

**What the agent can reach.** This is not a single read-only `GITHUB_TOKEN` for all work. By default, [the scope of Copilot's authentication token is limited to the repository where it is running](https://docs.github.com/en/copilot/tutorials/cloud-agent/give-access-to-resources). The agent [can push only to a `copilot/` branch](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) it creates, or to an existing pull request branch when it is mentioned with `@copilot`. It cannot run `git push` itself. The built-in [GitHub MCP server](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers) uses a separate, "specially scoped" token with **read-only** access to the current repository unless you replace it with a wider personal access token or a GitHub App. The Actions `GITHUB_TOKEN` used in `copilot-setup-steps.yml` is the usual [per-job installation token](https://docs.github.com/en/actions/concepts/security/github_token): unique to the job, limited to that repository, and expired when the job ends (at most six hours on GitHub-hosted runners). Do not treat that setup-steps token as the agent's only credential, and do not widen the default GitHub MCP token unless the task needs it.

**Firewall and MCP tools.** The [agent firewall](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall) is on by default and is meant to limit exfiltration, but it applies only to processes the agent starts with its Bash tool. It does **not** apply to MCP server processes or to steps in `copilot-setup-steps.yml`. Repository MCP servers are configured as JSON under repository settings (Copilot, then MCP servers), with a `tools` allowlist per server. GitHub "strongly recommend[s] that you allowlist specific read-only tools," because the agent will use enabled tools on its own, without asking. Secrets and variables for those servers must be named with a `COPILOT_MCP_` prefix and stored as [Agents secrets](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/configure-secrets-and-variables) (the Copilot / `copilot` environment). Official examples often pin MCP packages at `@latest`. That is the tool-description risk @rachbelaid raised: pin and review server versions, and re-review the tool list when a server changes.

**Per-task tokens, workflows and cloud credentials.** For workflow jobs, mint [GitHub App installation access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation) as the per-task pattern: they expire after one hour, and you can narrow both the repositories and the fine-grained permissions below what the app itself was granted. [GitHub Agentic Workflows](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows) default to read-only repository permissions; writes are limited to declared `safe-outputs` (for example `create-issue`, `add-comment`, `create-pull-request`), and proposed outputs are scanned before they are applied. Secrets are kept out of the agent runtime and used in isolated downstream jobs. For cloud providers, use [OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect) so the job exchanges a short-lived token with AWS, Azure or GCP, instead of storing long-lived cloud credentials as GitHub secrets.

**Audit and revocation.** Enterprise audit logs can be filtered with `actor:Copilot`. Agentic events set `actor_is_agent` to true, include an `agent_session_id`, and record in the `user` field [the person who initiated the session](https://docs.github.com/en/copilot/reference/enterprise-administrators/agentic-audit-log-events). That is attribution, in @johnroodepic's sense: it fixes the log. It does not shrink what a compromised session can do. When an employee leaves or loses access, revoke the GitHub App installation, the Agents secrets they owned, and any OIDC trust or PAT that was minted for their agents. Do not rely on the audit trail alone.

**A practical factory shape.** Give each factory role its own identity: an implementer coding agent, a reviewer, and a scheduled cleanup workflow should not share one service account or one wide MCP token. That can be separate GitHub Apps, or separate Agentic Workflows with their own `permissions`, `tools` and `safe-outputs`. Scope each run with a short-lived token (installation token, job `GITHUB_TOKEN`, or OIDC). Allowlist tools per MCP server, and pin the server version. Tie revocation to the human owner, so delegated access does not outlive their account.

This is the open question already noted in [MCP or CLI? Yes. (@zeeg)](2026-11-10-zeeg-mcp-or-cli.md): token scope is still something you have to design, even when the transport is settled. It also matches [@andrestaltz](2026-11-10-andrestaltz-software-factory-lessons.md) on failing closed and not automating a sloppy inner loop, and the done-gate warning in the [@bebuu_ai harness note](2026-11-11-bebuu_ai-claude-harness.md): a named identity with a stub check is still a stub.
