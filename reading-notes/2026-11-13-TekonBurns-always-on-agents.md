## What the guide argues

An always-on agent is a user experience, not a process that runs all day. The agent "spends most of its time asleep, waking up periodically to do work." A **run** is one stretch of work: the agent receives an event, does the task, and saves what happened. A run happens inside a **session**, which is the transcript of messages and tool calls. When the run finishes, the agent sleeps, and the cycle repeats.

The surrounding architecture has five primitives: event inbox, timers, memory, permissions, and outbox. Underneath, the agent still uses the same core loop as any other agent. The primitives control when it wakes, what carries over between runs, and how work reaches the user.

The introduction also claims that on one long-horizon coding benchmark, Opus 5.5 cost 78% less per solved task than Opus 5, against 40% less on typical workloads. That is Anthropic's own figure, not independently checked here, and it is not part of the five primitives.

## The five primitives

**Event inbox.** Do not let each event source call the agent directly. Two events at once can start competing runs, and a crash can lose an event. Every source writes to an inbox; a worker picks work from there. The simplest shape is a durable list (usually a database table), a handler (usually an HTTP endpoint) that appends events, and a worker that reads pending rows.

The handler should acknowledge quickly, because some webhook providers treat a slow response as failure. Lightweight checks are fine in the handler; deeper work such as prompt-injection checks belongs in the run. Events can be deduplicated by unique identifiers from the source. The inbox, not the in-memory worker, is the source of truth: if the worker dies mid-run, a new one pulls the latest pending events and can retry. Start with one inbox per user, and split later if you need more parallelism. An inbox should have only one active worker at a time.

Events that continue earlier work, such as a user reply, resume an existing session; everything else starts a new session. The worker should batch pending events (several messages in a row become one run). If a new event arrives mid-run, you can push it to the next run, fold it into the current run, or interrupt and restart.

**Timers.** These make the agent proactive. A **follow-up** is a deadline the agent sets for itself (check in on a reply). A **schedule** is a recurring task on a known cadence (a daily newsletter). Timers live in their own durable store, separate from the inbox, because the inbox should only hold work that is ready now. A schedule also has to track recurrence. A timer does not start a run on its own. A scheduler polls the store, marks a follow-up done or rolls a schedule forward to the next due time, then injects an event into the inbox and wakes the worker. You can build the scheduler or use a durable execution engine.

**Memory.** Continuity across disjointed runs needs its own store. In Claude Code's auto memory and the Messages API memory tool this is a directory of files; for an always-on agent those directories should map to durable storage (a database or object store) so memories outlive the worker.

The rule of thumb: store only what the agent cannot look up again. If it already lives in an issue tracker, save a pointer. Four kinds of memory:

- User instructions: their own file, loaded at the start of every run, because the user will not always be there to steer.
- User notes: role, preferences, corrections. Start with one file; as it grows, split into small files and load only an index at wakeup, pulling a file when needed.
- Past messages: so the agent does not repeat itself. Either a file loaded at the start of each run, or the worker loads the last few messages.
- Task progress: for each ongoing task, what is done and what is left, so a new run can continue. As with notes, load an index and pull detail on demand.

Before work starts, the agent loads the system prompt, tool definitions, and memory files. That overhead is in every run, so keep it lean and use prompt caching. A new session starts with only that overhead plus the triggering events. An existing session also brings back earlier messages and tool calls. If a session grows too long, compact older messages or start a new session. Both lose detail, so anything that must persist should already be in memory.

The guide also adds **dreaming**: a pass that reviews past sessions to curate memories, replace outdated entries, and find patterns that only show up across many runs. The always-on guide does not specify the algorithm. It points to Anthropic's earlier post [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory) (6 Nov 2026) for more detail. That post describes dreaming as offline compute that can correct notes against transcripts, build representations such as wikis, promote a small index into the next session, and fill gaps. It also warns that an incorrect injected note can be carried into every session, and that a representation can grow larger than the source.

**Permissions.** A run holds the user's access and operates unattended, so this is where the design carries the most risk. For each tool call the agent must proceed, block, or wait for approval. Three components:

- Credential store: do not keep passwords or access tokens in the agent's environment. A proxy outside that environment adds credentials to outgoing requests. The agent sends requests without credentials; the proxy injects them before forwarding.
- Auto mode: classifiers review higher-risk actions and block the dangerous ones so the agent can try a safer approach. User review is still needed for the most important decisions. The guide points at Claude Code's auto mode as the existing version of this.
- Deferred tool calls: a hook can defer a call and wait for clarification or approval. The run ends and the session is saved mid-call. The request is shown to the user (the guide mentions an interactive card built with MCP Apps). The user's answer comes back as an event in the inbox. That event starts a new run, which resumes the saved session with the user's input. While the deferred call is waiting, the worker can pick up other events, so the agent is not blocked.

**Outbox.** Unlike a chat agent, an always-on agent does most of its work in the background. The user gets the outcome and a few details, not the whole step-by-step. A run ends in one of three ways: the agent sends a message to the outbox, it decides that nothing needs to be sent, or it uses a deferred tool call. Most agents can get by with a "send" tool that delivers directly. You only need a formal outbox (a table of outgoing messages plus a dispatcher, analogous to the inbox and worker) when you want to pace messages or recover from delivery errors. A deferred-approval request can go through the outbox or be shown directly in the interface. The guide recommends evals to tune volume, and says it is better for the agent to start quiet and earn attention over time.

The five pieces form a cycle. Every run starts from an inbox event (user message, webhook, or timer). The worker starts a new or existing session, the agent reads memory, acts within its permissions, updates memory, and may push a row to the outbox. A run can set a timer that wakes it later. A user reply lands back in the inbox. Each run is brief; the cycle is what feels always on. The guide has no separate observability section.

## What checks out against the post

The post's main claim is right: always-on agents sleep, wake for short runs, save state, and sleep again. The five headings match the guide.

A few compressions are worth flagging. The post says "one active worker per user." The guide's starting advice is one inbox per user, and one active worker per inbox. The post's "load a small index at wakeup, not every file" is what the guide says for growing user notes and task progress, not for user instructions, which are loaded every run. The formal outbox is optional in the guide; it is for pacing and error recovery, and "send nothing" is a valid end to a run. The post's "3 AM" example is colour, not a quote. The post also leaves out runs versus sessions, resume versus a new session, mid-run push/fold/interrupt, the inbox as source of truth, deduplication by source identifier, auto-mode classifiers, prompt caching, and how an approval wakes a sleeping worker (it is an inbox event that resumes the saved session). Idempotency keys for a crash after "email sent" and before "state saved" are not in the guide. The guide only says events can be deduplicated by source identifiers, and that an outbox helps recovery.

## GHCP mapping

This is a proposed mapping onto GitHub Actions, GitHub Agentic Workflows, and Copilot, not a claim that GitHub ships Anthropic's always-on architecture.

**Inbox.** [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) (and the same `on:` field in [Agentic Workflows](https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows)) are the closest thing to an inbox: `issues`, `issue_comment`, `pull_request`, `workflow_dispatch`, and `repository_dispatch` for activity outside GitHub. That is event delivery into a new workflow run, not a durable table that a worker polls. There is no built-in batching of rapid messages, and mid-run fold-into-the-current-run is not an Actions feature. If you ingest GitHub webhooks yourself (for example before creating a `repository_dispatch`), [dedupe on `X-GitHub-Delivery`](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks): it is a globally unique GUID, and a redelivery keeps the same value. [Re-running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs) replays the original event (same `GITHUB_SHA` and `GITHUB_REF`) and can be done up to 50 times within 30 days, so any side effect in the workflow must be idempotent across attempts, not only across webhook redeliveries. Put an idempotency key in safe-output bodies or labels so a retry does not create a second comment or issue.

**One worker per inbox.** An Actions [`concurrency` group](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) (for example per issue, `group: agent-${{ github.event.issue.number }}`) allows at most one running job or workflow in that group. That is the practical single-writer lock. `cancel-in-progress: true` is the guide's interrupt-and-restart. Leaving it false queues the next run (the default pending queue is one; `queue: max` allows up to 100 pending). Default pending behaviour replaces an existing pending run, so it is not a perfect "push every event to the next run" inbox.

**Timers.** Actions [`schedule`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) (cron, UTC by default, shortest interval five minutes) covers recurring schedules. [gh-aw fuzzy schedules](https://github.github.com/gh-aw/reference/schedule-syntax/) (`daily`, `daily around 14:00`, `weekly on monday`, and similar) are documented and scatter times so many workflows do not hit the same minute. There is no first-class store for an agent-set follow-up. A one-off "check this tomorrow" timer would have to be something you build, for example a row in repo-memory plus a scheduled poller that injects a `workflow_dispatch` or a comment, which is a pattern, not a built-in.

**Memory.** [Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory) stores repository-level facts (scoped to that repository) and user-level preferences. Default expiry is 90 days without reinforcement; enterprise or organisation owners can set repository-fact retention between 7 and 180 days; user preferences always use the default. The timer resets when Copilot upvotes a memory, not when the memory is merely retrieved. Copilot is instructed not to store short-lived or task-specific instructions, and it cannot itself delete a memory on request (it can downvote; a person deletes it in settings). Use custom instructions for standing rules. For workflow-owned state, [gh-aw cache-memory](https://github.github.com/gh-aw/reference/cache-memory/) uses the Actions cache (about seven days unused, 10 GB per repository, LRU eviction, branch-scoped), and [repo-memory](https://github.github.com/gh-aw/reference/repo-memory/) stores files on a Git branch with unlimited retention and version history. Comment-memory is a third, comment-backed store. Standing files in the repo (`AGENTS.md`, instructions) are the "user instructions" file that should load every run.

There is no built-in dreaming pass. Copilot Memory expiry and voting retire unused facts; cache-memory expires. That is not a review of past sessions. A practical substitute is a scheduled "memory tidy" workflow that opens a pull request against the memory branch, so a wrong deletion is reviewable, which is the check @open_is_free asked for.

**Permissions and deferred approval.** [Agentic Workflows are read-only by default](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows). Writes go through declared `safe-outputs`, proposed outputs are scanned, and secrets stay out of the agent runtime in isolated downstream jobs, which is the closest documented match for a credential proxy. Human approval: an [environment with required reviewers](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) can hold a job in a waiting state until one of up to six reviewers approves (optional prevent-self-review; waiting jobs fail after 30 days). That continues the same job after approval. It is not the guide's "run ends, session is saved mid-call, approval returns as an inbox event, a new run resumes the session." For the Copilot coding agent, [the assigner cannot provide a counting approval](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output), Copilot cannot approve or merge its own draft pull requests, and [an extra approval is required](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) when Copilot opens a pull request under its own app identity if the repository already requires at least one (on by default in rulesets; always on for classic branch protection). There is no documented GHCP equivalent of Claude Code auto-mode classifiers for unattended tool calls.

**Outbox.** `safe-outputs` are the write path (`add-comment`, `create-issue`, `add-labels`, and the rest; see the [safe-outputs reference](https://github.github.com/gh-aw/reference/safe-outputs/)). Per-run `max` limits cap how many comments or labels one run can emit. That is a volume cap, not a dispatcher that paces messages over hours or holds a 3am note until morning. GitHub has no built-in outbox table. `hide-older-comments` and `replace-older-comments` can reduce noise, but they are not pacing. If you need the guide's outbox, you would persist intended messages (repo-memory or a draft issue) and let a scheduled dispatcher workflow deliver them.

A practical factory shape: trigger agentic workflows from issue, comment, pull request, and `repository_dispatch` events; set a concurrency group per issue; use `schedule` or a gh-aw fuzzy schedule for recurring work; keep standing rules in instructions and run state in repo-memory; put side effects behind safe-outputs with an idempotency key; hold risky jobs on an environment that needs a reviewer; run a scheduled memory-tidy workflow that opens a pull request rather than deleting quietly; and do not treat a successful workflow run as proof that a delivery was acknowledged by the agent.
