# Find state machines, check their rules, then show the flows (@poteto)

Source: [@poteto, 8 Nov 2026, 20:02 Europe/London](https://x.com/poteto/status/2119521036660314339), quoting [@steveruizok, 31 Oct](https://x.com/steveruizok/status/2116552016218710389): "find all of the implicit state machines in my app". The follow-up is one formal-verification skill per subsystem, then statecharts for important user flows. This is a workflow, not evidence that arbitrary app code is now proved correct.

## What pstack actually does

Primary sources read on 8 Nov: the three linked skills, statechart launcher/CLI and rendering reference, and regular verification feature-map examples. These are live `main` links, not frozen release documentation.

- **[/create-formal-verification-skill](https://github.com/cursor/plugins/blob/main/pstack/skills/create-formal-verification-skill/SKILL.md)** selects a costly failure that tests struggle to reach, verifies a property, and writes a project-local skill. TLA+ is the default for event ordering; other options are a code verifier, SMT-backed verifier or proof assistant, chosen for the question. The current instructions do not prescribe Lean, Alloy or Quint. If no code verifier fits, they ask for generated-input tests on real code, not a hand-modelled function. Each subsystem skill should record covered files/functions, assumptions, bounds, pinned tooling, one rerun command and a sync commit. It must catch a deliberate scratch break in real code before hand-off. Existing defects remain findings, not permission to change product code.
- **[/statechart](https://github.com/cursor/plugins/blob/main/pstack/skills/statechart/SKILL.md)** writes a TLA+ spec/config and optional view module, runs TLC, then produces `report.md`, Mermaid `chart.mmd` and TLC logs. Its TypeScript helper needs a supported runtime; first use installs Java/TLC through mise. [Rendering](https://github.com/cursor/plugins/blob/main/pstack/skills/statechart/references/render.md) uses Pele for SVG. Flat, nested and parallel-region charts are supported, not XState or SCXML exports. Above 500 model states, only bug paths are drawn; a passing large model gets no chart.
- **[/create-verification-skill](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md)** generates `.cursor/skills/verify-<app>/`, launch/doctor/drive/evidence/cleanup instructions, helpers and a feature map. It exercises one real feature end to end and retains proof after cleanup. This closely matches [@poteto's "regular one" reply](https://x.com/poteto/status/2119523322757325117); that identification is inferred, not an explicit skill name in the reply. It does not describe /statechart.

**Impossible states?** Answering @overshadowed_x: /statechart checks stated rules, marks reachable violations and deadlocks, and reports shortest counterexample paths. It does not infer all forbidden combinations or list every unreachable state. Unreachable states simply need not appear. A bounded model passing is not an implementation proof; reports can list rules not checked. Merged chart labels can hide detail or show `mayBreak` rather than `breaks`.

**Generated tests?** Neither skill promises a general chart-to-pytest/vitest generator. /statechart explicitly requires replaying bug paths against code as tests or live reproductions. The formal generator requires negative controls. @NixonPerinchery's transition-test point is the missing enforcement layer; @AlexeySolomonov's question is unanswered in the thread. A missing transition can be intentional, not necessarily a bug. @_yukungao's double completion and @VrajTalati1's late payment after cancellation are useful targets, not verified findings here.

## GHCP mapping for Sam's Python + TypeScript factory

Proposed port, not a pstack feature:

1. Add a [Copilot skill](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills) at `.github/skills/model-subsystems/SKILL.md` and a [custom agent](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/create-custom-agents) at `.github/agents/state-review.agent.md`. Adapt Cursor paths and invocation rules, preserve upstream licensing. Instructions require the chain: inventory implicit machines with code locations; generate one verified skill per subsystem under `.github/skills`; chart only key flows. Do not assume Cursor slash commands transfer unchanged.
2. Start with auth/session revocation, payment/cancellation races, queue retries/leases and agent-run cancellation/completion. Include cross-subsystem delayed or duplicate events. Store models/configs/views under `verification/<subsystem>/` and copy them to scratch for chart runs.
3. Give each transition a stable ID and reviewed table: source state, event, guard, destination, side effects. Generate parametrised pytest and vitest cases from that table, not the lossy Mermaid picture. Assert persisted backend state, visible frontend state, forbidden events and duplicate/delayed sequences. Replay each counterexample, including cancelled checkout receiving payment and completion firing twice.
4. Pin checker/runtime versions in setup. Run the same verification command in Actions on every PR; require its named check through branch protection. Fail on violations, errors or incomplete checks. Upload reports/logs even on failure. Keep the code coverage/sync record current; a green stale model is insufficient.
5. Commit specs, transition tables and Mermaid/SVG as reviewable PR artefacts alongside tests. Agentic Workflows can propose refresh PRs when covered files change, with restricted permissions and human review. Deterministic Actions remain the merge gate, not an agent's prose verdict.
